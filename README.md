# ZET 017 — разделение на две библиотеки

*[English version](README.en.md)*

Разбор XML вынесен из основной библиотеки в отдельный модуль. Основная
библиотека `zet017tcp` больше не зависит от libxml2.

## Происхождение и лицензия

Проект основан на библиотеке [zetlab/zet017tcp](https://github.com/zetlab/zet017tcp)
и распространяется на тех же условиях — MIT, `Copyright (c) 2023 ZETLAB`,
полный текст в файле `COPYING`.

Это не форк репозитория, а самостоятельная работа на его основе: структура
каталогов изменена — библиотека перенесена в `zet017tcp/`, рядом добавлен
модуль `zet017config/`. Построчное сравнение с оригиналом поэтому
неинформативно, и ниже перечислено, чем эта версия от него отличается.

**Публичный API оригинала сохранён полностью.** Все четырнадцать его функций
на месте, с прежними сигнатурами и кодами возврата. Добавлено шесть новых.

**Новый модуль `zet017config`.** Чтение и запись `devices.cfg`. Зависимость от
libxml2 изолирована в нём, поэтому основная библиотека остаётся без внешних
зависимостей. В оригинале такого модуля нет.

**Журналирование.** Текстовый лог с четырьмя уровнями важности и независимым
порогом для каждой из четырёх категорий сообщений. Добавлены
`zet017_server_create_ex`, `zet017_server_set_log_level`,
`zet017_server_set_log_category_level`, `zet017_server_set_log_file`.

**Чтение всех каналов за один вызов.** `zet017_channel_get_all_data` и
`zet017_channel_get_all_frame_data` снимают все активные каналы под одним
захватом мьютекса, из одного окна кольцевого буфера. При поканальном чтении
мьютекс отпускается между вызовами, и поток приёма успевает затереть начало
окна — первый канал оказывается прочитан до перезаписи, последний уже после.
Функции различаются только раскладкой приёмника.

## Идея

- `zet017config.dll` — две функции: `zet017_config_load_file(...)` читает XML в
  структуры `zet017_cfg_config` / `zet017_cfg_tenso_config`, а
  `zet017_config_save_file(...)` пишет их обратно в файл. С устройством модуль
  не общается вовсе.
- Отправку выполняет клиент через `zet017tcp.dll`
  (`zet017_device_set_config` / `zet017_device_set_tenso_config`).
- Структуры в обоих заголовках бинарно идентичны (проверено `offsetof`/`sizeof`
  на x86 и x64), поэтому указатель безопасно приводится между модулями.

## Архитектура: Opaque Pointer, «тихий указатель» и плоский C-ABI

Библиотека построена вокруг двух требований, определяющих остальные проектные
решения: детерминированное поведение при частично заданных аргументах и
вызов из среды, которой доступно только разрешение символа по имени и
передача аргументов по двоичному соглашению.

### Паттерн «Opaque Pointer» и сохранение состояния

Сеанс работы с устройством не укладывается в один вызов. После возврата из
`zet017_server_add_device` продолжает работать рабочий поток: он держит
открытыми командный и потоковый сокеты, переподключается при обрыве и
непрерывно заполняет кольцевой буфер АЦП. Следующий вызов
`zet017_channel_get_all_data` обязан попасть в то же самое состояние —
в те же сокеты, тот же буфер, те же счётчики.

Следовательно, состояние должно пережить возврат из функции DLL. Хранить его
на стороне вызывающего невозможно: это `mutex_t` и `cond_t`, дескриптор
потока `thread_t`, сокеты `socket_t`, `FILE*` журнала и кольцевой буфер на
несколько мегабайт. Все они объявлены условно по платформе —
`CRITICAL_SECTION` против `pthread_mutex_t`, `HANDLE` против `pthread_t` —
и различаются размером и раскладкой между сборками. Представления в LabVIEW
или Python у них нет, и оно не требуется: эти типы существуют только внутри
реализации на C.

Поэтому распределение памяти и владение ею целиком на стороне библиотеки:

1. `zet017_server_create` выделяет `struct zet017_server`, помещает указатель
   в статический реестр `g_servers` внутри DLL и возвращает индекс слота как
   `zet017_handle`.
2. `zet017_server_add_device` выделяет `struct zet017_device`, запускает для
   него рабочий поток и включает устройство в список сервера.
3. Каждый последующий вызов преобразует `handle` обратно в указатель
   (`registry_get`) и работает с теми же структурами.
4. `zet017_server_free` освобождает всё и обнуляет `*handle`.

Вызывающая сторона хранит между вызовами единственное значение — `int32_t`.
Никакой памяти под состояние сеанса она не выделяет и ничего не освобождает.

Практическое следствие для LabVIEW: дескриптор помещается в сдвиговый регистр
и передаётся от итерации к итерации. Его потеря означает утечку —
структуры остаются в реестре, рабочие потоки продолжают работу, файл журнала
остаётся открытым (см. раздел про кнопку Abort Execution).

### Паттерн «тихий указатель» (silent pointer)

Каждый указатель публичного API отнесён к одной из двух категорий, и
категория неизменна для всего времени существования функции:

- **Обязательный** (required, non-nullable). `NULL` трактуется как отказ:
  функция возвращает отрицательный код и не производит побочных действий
  (side effects). Исключены частичная запись в буфер, частично изменённый
  файл и изменённое состояние устройства — отказ соответствует строгой
  гарантии «всё или ничего» (all-or-nothing).
- **Необязательный, он же тихий** (optional, nullable). `NULL` означает, что
  соответствующая часть работы не требуется. Функция пропускает её и
  возвращает 0; с точки зрения этой части вызов представляет собой холостую
  операцию (no-op). Это штатный сценарий, а не подавленная ошибка.

Правило выдерживается во всём API:

| вызов | результат передачи `NULL` |
|---|---|
| `zet017_server_create(&h, NULL)` | сервер создан, файловое журналирование отключено |
| `zet017_server_set_log_file(h, NULL)` | журналирование отключено, файл освобождён |
| `zet017_config_load_file(..., tenso_config = NULL)` | секция `<Channels>` не читается |
| `zet017_config_save_file(..., tenso_config = NULL)` | секция `<Channels>` в файле не изменяется |
| `zet017_channel_get_all_data(..., channels = NULL)` | число каналов не возвращается |

Тот же принцип распространён на данные, а не только на указатели. При чтении
конфигурации отсутствующий в файле элемент оставляет поле структуры без
изменений; при записи отсутствующее в структуре значение не приводит к
созданию элемента в файле. Данные, которыми модуль не управляет, проходят
через него без модификаций (pass-through).

Следствие для вызывающей стороны: не требуется формировать фиктивные
аргументы ради полноты сигнатуры и не требуется классифицировать отказы по
степени тяжести. Отрицательный код возврата означает, что не выполнено
ничего; ноль — что выполнено ровно затребованное.

### Основания для вызова из произвольного языка

Заголовочные файлы не содержат конструкций, специфичных для C++: классов,
шаблонов, перегрузки функций, исключений и ссылок. Как следствие, отсутствует
декорирование имён, из-за которого символ в таблице экспорта DLL перестаёт
совпадать с идентификатором в исходном тексте.

Состав решений:

- **Соглашение о вызове.** `ZET017_TCP_API` раскрывается в `int __stdcall` —
  соглашение, применяемое функциями WinAPI и ожидаемое средствами импорта на
  32-разрядной Windows. На прочих платформах макрос раскрывается в `int`.
- **Экспорт через `.def`.** Имена размещаются в таблице экспорта без
  декорирования: `zet017_device_get_config`, а не
  `_zet017_device_get_config@12`. `CMAKE_WINDOWS_EXPORT_ALL_SYMBOLS` отключён
  намеренно; `win32/*.def` — единственный источник истины по составу
  экспорта.
- **Opaque Pointer** — см. отдельный подраздел ниже. Наружу передаётся
  `zet017_handle`, представляющий собой `int32_t`; значение `0`
  недействительно.
- **Только POD-структуры** (plain old data). Целочисленные типы
  фиксированной ширины объявлены в заголовке явно, без `<stdint.h>`:
  системный заголовок MSVC не является самодостаточным, и синтаксические
  анализаторы заголовков не могут его обработать. Описание ABI при этом
  остаётся полным.
- **Отсутствие обратных вызовов** (callbacks). Обратная связь реализована
  опросом (polling): вызывающая сторона самостоятельно считывает состояние
  (`zet017_device_get_state`) и данные в заранее выделенный ею буфер.
  Библиотека не передаёт управление внешнему коду и не возвращает память,
  подлежащую освобождению вызывающей стороной.
- **Диагностика только кодами возврата.** Исключения, `errno` и глобальное
  состояние ошибки не используются.

Перечисленное образует плоский C-ABI, с которым единообразно работают
LabVIEW, C#, Python, Delphi, Rust и прочие среды, располагающие FFI:

```csharp
// C#
[DllImport("zet017tcp.dll", CallingConvention = CallingConvention.StdCall)]
static extern int zet017_server_create(ref int handle, string logPath);
```

```python
# Python: на Windows именно WinDLL — это stdcall
import ctypes
lib = ctypes.WinDLL("zet017tcp.dll")
h = ctypes.c_int32(0)
lib.zet017_server_create(ctypes.byref(h), None)   # None — тихий указатель
```

Особенности импорта в LabVIEW рассмотрены в отдельном разделе ниже.

## Последовательность на стороне клиента (LabView)

Настроить устройство из файла:

1. `zet017_device_get_config` / `get_tenso_config` — взять заводскую конфигурацию;
2. `zet017_config_load_file` — наложить значения из XML;
3. `zet017_device_set_config` / `set_tenso_config` — отправить на устройство.

Сохранить текущие настройки обратно в файл:

1. `zet017_device_get_config` / `get_tenso_config` / `get_info`;
2. `zet017_config_save_file(каталог, имя файла, info.serial, ...)`.

## Чтение данных с каналов

Кольцевой буфер АЦП наполняет рабочий поток устройства, а позицию чтения
ведёт клиент. Библиотека её не хранит: `zet017_state.pointer_adc` — это
позиция **писателя**, приведённая к отсчётам на канал.

Все три функции чтения принимают `pointer` и `size` в отсчётах на канал и
читают **назад** — возвращается окно `[pointer - size, pointer)`.

### Поканально и все каналы разом

| функция | раскладка `data` |
|---|---|
| `zet017_channel_get_data` | один канал, `data[i]` |
| `zet017_channel_get_all_data` | `data[k * size + i]` — отсчёты канала подряд |
| `zet017_channel_get_all_frame_data` | `data[i * n + k]` — каналы вперемежку, как в кольце |

Здесь `n` — число активных каналов, оно же возвращается в `channels`.

Читать все каналы одним вызовом стоит не ради удобства. При поканальном
чтении внутренний мьютекс отпускается между вызовами, и поток приёма
успевает затереть начало окна: первый канал оказывается прочитан до
перезаписи, последний — уже после, то есть из следующего оборота кольца.
Функции `..._get_all_*` снимают все каналы под одним захватом, из одного
окна. Для расчётов, где каналы сравниваются между собой (измерительный
против опорного), это обязательное условие.

Обе раскладки дают одни и те же числа и различаются только порядком.
Планарная не требует перекладки ни в C, ни в LabView; чередующаяся
повторяет порядок кольца и копируется внутри DLL примерно на 40 % быстрее,
но раскладывать её приходится вызывающему.

### Соответствие строк каналам

`k` — порядковый номер среди **включённых** каналов, а не номер канала.
При `mask_channel_adc = 0b101` (каналы 0 и 2) `k = 0` это канал 0, а
`k = 1` — канал 2. Соответствие восстанавливается из
`zet017_config.mask_channel_adc`, число активных каналов возвращает
параметр `channels`.

### Размер буфера

Буфер выделяет вызывающий, минимум `channels * size` элементов `float`.
Библиотека не может узнать размер чужого буфера, поэтому требует
`capacity` — сколько элементов в нём помещается. Если мало, возвращается
−7, в `data` не пишется ничего, а в `*channels` попадает требуемое число
каналов: так узнают нужный размер, не угадывая. `channels` можно передать
`NULL`, если он не нужен.

### Коды возврата `..._get_all_*`

```
 0  успех
-1  невалидный handle или устройство не найдено
-3  нет связи с устройством
-4  data == NULL
-6  pointer или size выходят за размер кольцевого буфера
-7  capacity мала (в *channels — требуемое число каналов)
```

### В LabView

- `zet017_channel_get_all_data` — параметр `data` объявляется как
  **2D Array of Single** с передачей Array Data Pointer; строки каналы,
  столбцы отсчёты, нужный канал достаётся Index Array.
- `zet017_channel_get_all_frame_data` — **Array of Single** (1D);
  раскладка делается Reshape Array в (`size` × `n`) с последующим
  Transpose Array либо Decimate 1D Array.
- `channels` — указатель на U32; если значение не нужно, оставьте терминал
  неподключённым только при передаче `NULL`.

Сигнатуры обеих функций совпадают, поэтому для сравнения раскладок на
стенде терминалы CLFN не перевязываются — меняется только имя функции.

## Сохранение: файл-донор обязателен

`zet017_config_save_file` **не создаёт** файл, а обновляет существующий; если
файла нет, возвращается -2.

Причина в том, что настоящий `devices.cfg` заметно шире того, чем оперирует
модуль: около тридцати элементов на устройство и полутора десятков на канал,
`KodAmplify` из 32 позиций, отдельный канал-генератор. Эти значения приходят
от устройства в служебной структуре `zet017_device_info` (`zet017tcp.c`),
наружу она не отдаётся, и в `struct zet017_config` попадает лишь малая часть:

| элемент `devices.cfg` | поле `zet017_device_info` | есть в `zet017_config`? |
|---|---|---|
| `Amplitude`, `DigitalResolChanADC` | `resolution_adc[16]` | нет |
| `Atten` | `atten[4]` | нет |
| `DigitalInput/Output/OutEnable` | `digital_input`, `digital_output`, … | нет |
| `sizeInterrupt` | `size_packet_adc` | нет |
| `ChannelDAC` | `mask_channel_dac` | нет |
| `name`, `type`, `configTime` | `device_name` и метаданные ZETLAB | частично |

Поэтому запись обновляет только свои элементы, а весь остальной файл
переносит как есть — включая переводы строки в стиле Windows, отступы,
пробел в пустых тегах (`<AFCH />`) и кириллицу в атрибутах. Единственная
строка, которая меняется всегда, — объявление XML: к нему добавляется
`encoding="UTF-8"`, без чего libxml2 заменяет кириллицу в атрибутах ссылками
на символы (`№` превращается в `&#x2116;`).

Файл заменяется через временный, лежащий рядом, поэтому сбой записи оставляет
исходный нетронутым. Повторное сохранение тех же структур файл не меняет.

Что именно записывается и как разрешается приоритет «частота против сырого
кода» — в комментарии к функции в `zet017config.h`.

## Сборка

Основная библиотека (vcpkg НЕ нужен):
```
cmake --preset vs-x86      # или vs-x64
cmake --build out/build/vs-x86
```

XML-модуль (vcpkg подтянет libxml2 автоматически по vcpkg.json):
```
cmake --preset vs-vcpkg-x86
cmake --build out/build/vs-vcpkg-x86
```

Пресеты `vs-vcpkg-*` берут toolchain-файл из переменной окружения
`VCPKG_ROOT`, поэтому её надо выставить до конфигурации:
```
set VCPKG_ROOT=C:\vcpkg
```

`set` действует только до закрытия окна cmd. Visual Studio и CLion
запускаются отдельным процессом и такую переменную не увидят, поэтому
для работы из IDE задайте её постоянно и перезапустите IDE:
```
setx VCPKG_ROOT C:\vcpkg
```

То же самое делается через «Переменные среды» в свойствах системы.
Встроенный в CLion vcpkg лежит в `%USERPROFILE%\.vcpkg-clion\vcpkg`.

Если переменную задавать не хочется, переопределите `CMAKE_TOOLCHAIN_FILE`
в `CMakeUserPresets.json` рядом с `CMakePresets.json` — этот файл в
репозиторий не попадает.

## Развёртывание для LabView

- Всегда рядом с приложением: `zet017tcp.dll` (сама по себе, без зависимостей).
- Только если нужен разбор XML: дополнительно `zet017config.dll`
  + сопутствующие DLL libxml2 (проверить `dumpbin /dependents zet017config.dll`:
  обычно `libxml2.dll` и, при включённых фичах, zlib/iconv/lzma).
- Разрядность DLL должна совпадать с LabView (32-бит → x86-сборки).

## Подключение в LabView (Import Shared Library)

Оба заголовка (`zet017tcp.h` и `zet017config.h`) сделаны САМОДОСТАТОЧНЫМИ:
они не подключают `<stdint.h>`, а объявляют фиксированные типы вручную
(`zet017_uint32` и т.п. через `unsigned __int32`). Это нужно потому, что
мастер импорта LabView не всегда может разобрать системный stdint.h из
современного MSVC (ошибка "uint32_t not defined").

На первом шаге мастера указываются сама DLL и заголовок к ней:

![Выбор DLL и заголовка в мастере импорта LabVIEW](docs/labview-import-wizard.png)

Дальше по шагам мастера:
- Include Paths — можно оставить ПУСТЫМ;
- Preprocessor Definitions — оставить ПУСТЫМ;
- Calling Convention = **stdcall (WINAPI)**, т.к. API объявлен как
  `int __stdcall`. Мастер по умолчанию предлагает «C» — обязательно поменяйте.

### Минимальный пример

Блок-диаграмма полного цикла работы с устройством: создать сервер, добавить
устройство по IP, прочитать состояние, удалить устройство, освободить сервер.

![Блок-диаграмма LabVIEW: create_ex, add_device, get_state, remove_device, free](docs/labview-example-lifecycle.png)

Дескриптор сервера идёт по верхней линии от `create_ex` ко всем последующим
узлам и в конце к `free` — это и есть тот `int32_t`, который вызывающая
сторона хранит между вызовами. Кластер ошибки (нижняя линия) задаёт порядок
выполнения узлов: сами по себе функции DLL порядка не навязывают.

Два нуля на входах `create_ex` — это `handle` (заполняется функцией) и
`level` журналирования; числовые значения уровней приведены в разделе
о логировании.

Путь к журналу в примере указан относительным (`./log.txt`) ради компактности
диаграммы. В рабочем VI он должен быть **абсолютным**: текущий каталог у
LabVIEW непредсказуем — подробности в требованиях раздела о логировании.

## Логирование

`zet017tcp` пишет текстовый лог с уровнями важности и фильтром по категориям.
`zet017config` не логирует — там синхронный API и ошибки возвращаются кодом.

### Уровни и категории

Мастер импорта не переносит имена констант из заголовка, поэтому на входах
`level` и `category` в LabView будут обычные I32. Числовые значения:

| level | Имя | Что пишется |
|---|---|---|
| 0 | off | ничего |
| 1 | error | отказ ресурса или подсистемы |
| 2 | warning | + ожидаемые отработанные ситуации |
| 3 | info | + штатные события |

| category | Тег в файле | Что относится |
|---|---|---|
| 0 | `API` | вход/выход публичных функций, валидация аргументов |
| 1 | `NET` | подключение, обрывы, reconnect |
| 2 | `CMD` | выполнение команд устройства |
| 3 | `DATA` | поток АЦП: темп приёма, переполнение буфера |

Каждый уровень включает предыдущие. Удобно завести на стороне LabView
type-def Enum с этими значениями.

### Функции

```c
zet017_server_create(&h, "C:\\ProgramData\\zet\\zet017.log");        /* = create_ex(..., 3) */
zet017_server_create_ex(&h, "C:\\ProgramData\\zet\\zet017.log", 3);
zet017_server_set_log_level(h, 2);              /* всем категориям warning */
zet017_server_set_log_category_level(h, 0, 1);  /* API -> только error     */
zet017_server_set_log_file(h, NULL);            /* выключить и отпустить файл */
```

Типовая настройка для цикла сбора: уровень info всем категориям, а категории
`API` — error. Тогда спам `channel_get_data: entry/success` исчезает, а
сетевые события, ошибки команд и переполнение буфера остаются.

Сеттеры можно вызывать в любой момент из любого VI, параллельно с работающим
сбором.

### Формат строки

```
=== 2026-08-28 13:06:12 zet017tcp 1.0.1 (x86) log session started (level=info) pid=7412 exe=LabVIEW.exe ===
[2026-08-28 13:06:12.418] [INFO] [NET] connected (ip=192.168.0.55, name=ZET 058, serial=711347, reconnect #1)
[2026-08-28 13:06:41.902] [WARN] [DATA] adc buffer overrun (number=0, channel=0, behind=51200, size=4096, window=52488, lost=2808)
```

Время локальное, не UTC. Файл открывается на дозапись и не ротируется.
Баннер содержит PID и имя процесса: один и тот же файл могут писать среда
разработки LabView и собранный EXE одновременно, и по `pid=` строки
разбираются обратно.

Сообщение `adc buffer overrun` означает, что цикл опроса не успел за
устройством и часть запрошенного окна уже перезаписана: `lost` — сколько
кадров потеряно. Оно не чаще раза в секунду на устройство.

### Обязательные требования

**Режим потока Call Library Function Node — «Run in any thread».** По
умолчанию узел стоит в «Run in UI Thread»: тогда запись лога из
`channel_get_data` идёт в UI-потоке LabView, подвешивает фронт-панель и
сериализует вызовы всех VI. DLL потокобезопасна, ограничений на режим нет.

**Путь к лог-файлу — только абсолютный и только ASCII.** Текущая директория
у LabView непредсказуема: относительный путь ляжет либо рядом с
`LabVIEW.exe`, либо рядом с собранным EXE, а приложение под `Program Files`
писать рядом с собой не сможет. Разумные места — `%LOCALAPPDATA%` или
`C:\ProgramData\<приложение>\`. Кириллица в пути не поддерживается
(`fopen` работает с ANSI-кодовой страницей). Максимальная длина — 259 символов.

**Как узнать, что лог не открылся.** При `create`/`create_ex` неудача
открытия файла не считается ошибкой: сервер создаётся, лог молча
отключается — логирование не должно ломать инициализацию. Если нужен код
ошибки, создавайте сервер без лога и включайте его отдельно:

```c
zet017_server_create(&h, NULL);
int r = zet017_server_set_log_file(h, "C:\\ProgramData\\zet\\zet017.log");
/* r == -4: файл открыть не удалось или путь длиннее 259 символов */
```

**Кнопка Abort Execution.** Она не вызывает `zet017_server_free`: файл
остаётся открытым, рабочие потоки продолжают жить, а следующий Run создаёт
второй сервер и дописывает в тот же файл второй баннер. Это ожидаемо;
разбирать такие наложения нужно по времени и `pid=` в баннерах. Чтобы
отпустить файл штатно, вызывайте `zet017_server_set_log_file(h, NULL)` или
`zet017_server_free`.

## Важно при изменении структур

Определения `zet017_cfg_config` / `zet017_cfg_tenso_config` в
`zet017config.h` продублированы намеренно (независимость модуля). Если
поля `struct zet017_config` / `zet017_tenso_config` в `zet017tcp.h`
изменятся — синхронизируйте их и в `zet017config.h`.

По той же причине в `zet017config.c` продублированы таблицы перевода
«величина ↔ сырой код» (`zet017_cfg_get_mode_adc` и соседние). Сохранение
обязано разрешать приоритет полей ровно так же, как `zet017_device_set_config`,
иначе в файл попадёт не то, что уйдёт в устройство. Если таблицы в
`zet017tcp.c` (`zet017_get_mode_adc`, `zet017_get_sample_rate_adc`,
`zet017_get_rate_dac`, `zet017_get_amplify_code`) изменятся — поправьте и здесь.
